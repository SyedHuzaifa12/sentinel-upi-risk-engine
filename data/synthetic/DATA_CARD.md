# Data Card: Synthetic UPI Event Dataset

## What this is

Fully synthetic UPI (Unified Payments Interface) transaction events, generated by
`ml/src/generator/`. No real user, transaction, or institution data of any kind was
used to produce it — every payer, payee, VPA, device, and event is simulated from a
seeded random-number generator. This is not a sample or an anonymized extract of a
real dataset; it does not exist anywhere until the generator is run.

Regenerate with:
```
python -m ml.src.generator.cli --days 90 --payers 5000 --seed 42 --out data/synthetic/
```
Same seed → byte-identical output (see `ml/tests/test_generator.py`).

The event schema (`ml/src/generator/schema.py`) contains only fields a payment app
actually has at request time — no aggregates, no counts, no chargeback history, no
country field. Anything a real-time risk engine would need to *compute* from history
(fan-in, payee age, velocity, deviation from personal average) belongs in a feature
layer built on top of this data, never in the raw event itself.

## Why no public real UPI dataset exists

NPCI and the participating banks' transaction data is confidential financial
information, subject to RBI regulation and India's data-protection law (DPDP Act) —
it is not published, in raw or aggregate form, for research or benchmarking use.
Fraud-labeled transaction data specifically is even more sensitive than transaction
data generally: publishing which real patterns were flagged as fraud would hand
attackers a blueprint for evading detection. This is why "UPI fraud" datasets that
do circulate publicly (including the `UPI_FRAUD.csv` already in this repo, kept as a
legacy artifact) are not actually UPI data at all — they are card-fraud or generic
payment-fraud datasets, reformatted with UPI-sounding column names. That dataset's
100%-null `TransactionDate` column and its chargeback/foreign-transaction/high-risk-
country features (which don't exist on the UPI rail and are themselves post-outcome
information, not request-time signal) are direct evidence of that mismatch. This
generator exists because no substitute was available — not as a stopgap, but as the
only honest way to get temporally-structured, point-in-time-correct UPI-shaped data.

## Typologies encoded

Every typology below is encoded as a *relationship between multiple events* —
never as a single-row flag a naive classifier could key on directly (verified by
`ml/tests/test_generator.py::test_no_single_feature_column_leaks`).

- **MULE_FANIN**: a disposable-looking VPA (random letters + digits, no name
  structure) is created mid-simulation. 30-200 unrelated existing payers pay it
  within a 1-6 hour window — each individual payment looks completely ordinary
  from that payer's perspective (normal amount for them, normal device, normal
  initiation mode). Shortly after, the mule pays most of it back out to a handful
  of payees, then goes silent for the rest of the simulation. The only place this
  typology is visible at all is *fan-in per hour at the payee* — never in any
  single row.

  **Label split**: inbound events (victim → mule) are labeled `label_is_fraud=True`,
  `label_typology="MULE_FANIN"` — this is the actual detection target. Outbound
  events (mule → cash-out) are labeled `label_is_fraud=False`,
  `label_typology="MULE_OUTBOUND"` — retained in the event stream so fan-out /
  pass-through features are computable, but deliberately excluded from a training
  target. Rationale: on the outbound leg, the *payer is the mule itself*, so any
  payer-deviation feature computed there is meaningless; laundering detection
  (what happens to money after it lands in a mule account) is a different problem
  from payment-time fraud prevention (stopping the victim's payment before it
  happens), and conflating the two labels would blur that distinction.

- **SCAM_COLLECT**: a `COLLECT_REQUEST` sent to a payer who almost never uses that
  initiation mode, for 5-100x their personal average transaction amount, to a
  payee that's brand new to them — often, though not always, outside their normal
  active hours. The "not always outside active hours" is intentional: if it were
  always outside active hours, that single field alone would separate it.

- **ATO_BURST** (account takeover): a `device_id` the payer has never used before
  suddenly fires 3-8 payments within a 15-minute window, at an hour outside the
  payer's normal active window, with escalating amounts, all to payees the payer
  has never paid before.

- **QR_SWAP** — deliberately the hard case: an established merchant's *regular*
  payers (people who have that merchant as a recurring contact) suddenly pay a
  near-lookalike VPA (a one-character swap or insertion) at that merchant's normal
  hour-of-day and normal amount range. Nothing about amount, timing, or
  payment-frequency looks anomalous — only the payee VPA string differs, and only
  subtly. **This typology is intentionally near-invisible behaviorally.** The one
  partial signal available is that the lookalike payee is always "new to this
  specific payer" — but that alone is a weak signal here, because legitimate
  payees are also introduced steadily throughout the simulation (~15-25% of the
  legit payee population first appears after day 0, specifically so "payee new to
  payer" can't become a clean separator for *any* typology, QR_SWAP included).
  **Expect moderate, not zero, recall on this typology from any model trained on
  this data** — that's realistic. Real-world QR-swap fraud is notoriously hard to
  catch from transaction data alone, and a dataset that let a model catch it
  perfectly would be teaching a false lesson.

## Real-world signals that are absent

This generator does not attempt to simulate signals a real risk engine would also
have access to, because they don't exist in this synthetic environment and cannot
be fabricated meaningfully without real institutional infrastructure behind them:

- **Cross-institution / consortium fraud intelligence** — real risk engines share
  signal across banks and PSPs (e.g. "this VPA was flagged by three other banks
  this week"). There is only one simulated "institution" here, so no
  cross-institution graph exists.
- **KYC / identity-verification depth** — no document verification, no identity
  confidence score, no linked-identity graph (same person, multiple VPAs).
- **NPCI shared blacklists** — no simulated equivalent of an industry-wide
  known-mule or known-fraud-VPA registry.
- **Device-fingerprint depth** — `device_id` here is just an opaque identifier,
  not root/jailbreak detection, emulator detection, or a real fingerprint
  incorporating OS/hardware signals.
- **SIM-swap signals** — no telecom-side signal simulating a SIM swap
  independent of the payment app itself.
- **Dispute/chargeback outcome history** — deliberately absent per the schema's
  hard rule (these are the leaky, post-outcome features the legacy
  `UPI_FRAUD.csv` dataset relied on); a real system would eventually have
  resolved-dispute history to learn from, but only after the fact, never at
  decision time.

A model trained on this dataset should be understood as learning the behavioral
typologies that *are* encoded here, not as a complete simulation of every signal a
production UPI risk engine would have available.
